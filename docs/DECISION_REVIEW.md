# 從測試證據到 Gate 裁決

執行器只核對已列命令與判準，無法自行知道產品目標遺漏了什麼，也無法驗明正解來源可信、計畫選對產品或一個 JSON 是否代表整個測試套件。Agent 必須以實際專案與使用者目標補足這段判斷，不要求使用者先交新試點或工程文件。

規劃時，將與本次目標真正相關的重要失敗情境，簡短對照到需求來源、案例／既有證據，或排除／未知及其影響。依可達性、影響、現有防護與驗證成本決定優先級；不強迫所有專案測試同一份通用安全清單。已有充分且仍適用的證據可引用，不為數量重測。

預期值要能回到業務要求、規格、使用者裁決或外部契約的具體位置。實作、測具、預期共用同一假設時，增加獨立可核的例子或反例；無法確認就保留未知。若規格有誤，記錄變更理由與原失敗，不能事後改預期來洗成通過。接既有測試套件時，另核目標、必要案例、實跑／跳過與原始報告；`exit_code` 不提供套件案例數。

| 訊號 | 可支持的結論 | 仍須判斷 |
|---|---|---|
| PASS | 該命令的完整 JSON、退出碼與 stderr 符合預設判準 | 正解是否可信、重要案例是否漏列、是否測到真正產品 |
| EXIT_MATCH | 退出碼與預設 stderr 相符 | 案例可能零個、選錯、跳過或失敗被包裝器吞掉；不能稱行為 PASS |
| FAIL | 觀察違反計畫判準 | 產品缺陷、測具錯誤、警告／環境、需求錯誤分開歸因 |
| INCONCLUSIVE／NOT_RUN | 無法判定／沒有執行 | 哪些需求與決策受阻、是否已有副作用、能否安全另跑 |
| integrity／judgment_recheck MATCH | 包內身分、人口及重算判讀吻合 | 不是原始執行的獨立見證或不可偽造證明 |
| requirements_status | 所列需求的所列檢查是否全部行為 PASS | 沒有宣稱需求完整或產品已驗收；`goal_completion` 固定為未由執行器裁定 |

疑點成立、影響程度及是否值得修正分別裁決，合併同根因。每個需要處理的發現保留版本／場景、有效需求、預期與實際、可核證據、影響、反證、分類與優先級；可用精簡表格，不必為每項再建 Gate。

- 只有 stderr 警告：先確認警告與計畫差異；不能單憑 FAIL 稱 bug。精確預期警告須在執行前固定，未知內容不通用忽略。
- 測具選錯專案或空套件 rc0：先裁定測具／整合問題，不把它當產品通過或產品漏洞。
- 需求要求拒絕非法輸入，真實產品卻接受：有可信正解與可達重現時可認定產品缺陷；是否安全問題另看攻擊前提及影響。
- 可信命令能執行、沒有承諾的隔離不存在、使用者可重造整包：按既定信任邊界評估，不直接貼 RCE、逃逸或密碼學漏洞標籤。
- Windows 孫程序、脫離程序群組、副作用或外部依賴：已揭露不代表影響消失；若本次目標依賴完整停止／隔離／固定依賴，就不能據此工具宣稱已驗證，改用有相應能力的環境或保留受阻結論。
- 個人風格或合理設計取捨：沒有需求違反與實質影響時，不算 bug；可裁定維持不變。

最終交付先回答目標重要風險哪些有證據、哪些未測及影響，再列確認缺陷、測具／環境、限制／取捨、未知、撤回或降級。只有影響該決策的不確定性才阻擋該 Gate；案例數、報告數或多個 Agent 同意不會自動推進 Gate。本指引也不保證任何模型一定正確分類，實際遵循效果依本次執行證據成立。
