# 公開預覽版的需求與設計

目前目標：個人、開發者、企業與 Agent 可在有合法測試權限的本機專案上進行 QA，包括商業產品、企業內部系統及合法開發維護中的附帶品質驗證，交付可核對的結果。不依賴作者帳戶、歷史聊天或未發行內部路徑；商業使用許可不增加執行器的隔離或整合能力。

| 驗收需求 | 行為情境 | 設計／驗證 |
|---|---|---|
| 可開始 | 乾淨資料夾，Python 符合版本 | doctor → demo → verify；搬移與含空白／中文路徑驗證 |
| 可測別的專案 | 目標放在工具外，需求有來源 | project-root＋明列 files；實際子程序呼叫範例副本 |
| 不把命令成功當 QA | rc 0 但 JSON 錯、空輸出或僅 exit_code | 完整 JSON 判讀；EXIT_MATCH 與 PASS 分開 |
| 計畫與執行相符 | 來源、執行器、工具或環境變更 | 執行前、逐項前後核對；不自動重新批准 |
| 保留失敗與未測 | 第一項 FAIL、逾時、截斷 | 原始輸出保留；後續 NOT_RUN；新 attempt 才能另跑 |
| 證據可攜 | 原專案不在，證據搬到別處 | manifest 人口核對、重算判讀及報告；不是原始執行見證 |
| 跨 Agent | Codex、Claude、其他本機 Agent | 共用 START_HERE＋AGENTS；CLAUDE 匯入；真跨客戶端驗收另列狀態 |
| 產品 QA 可商用，兩類對外商業化受限 | 企業內部與合法開發維護可用；獨立營利 QA／對外營利 QA 平台另授權 | 自訂 LICENSE 2.0 與情境對照，不標成 MIT／Apache 或 OSI 開源 |

確定性核心只負責計畫、直接命令收據、有限判讀及包內核對。Agent 負責理解需求、規劃測試、解釋結果與影響；人類保有目標、授權、規格及驗收決定。受測程式、測具、工具與證據皆在同一使用者控制下，不提供獨立保管或不可偽造執行證明。

這是沿用 AKC「需求—版本—原始輸出—判讀—限制」理念的公開後繼，提供可信本機程式的直接命令 profile。沒有將內部未合格隔離 runner 改為合格，也沒有搬出內部私有案例或把過去產品結果轉給本版。舊版較強隔離契約並不由本 profile 繼承。

判定層次依次為：特定測試是否符合指定判準、證據在既定核對範圍是否完整、整體產品是否符合需求、是否正式驗收、是否有獨立安全審計。它們需要各自的證據與決策，不能逐層自動升格。授權也不會讓使用者的產品原碼、資料或報告自動改受 AKC 原始碼條款支配。

執行前需信任目標與命令。機器不強制網路或檔案權限，來源只是前後 hash 觀察，不能防止瞬間改寫後恢復，不能證明所有依賴。POSIX 程序群組清理是盡力措施；Windows 只結束直接子程序。需要 hostile code 隔離、瀏覽器或資料庫 E2E 時，應使用另有實測與適用授權的環境。
